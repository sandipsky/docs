# 14 Primary Keys

## What is it?

A **primary key** is the column (or combination of columns) that identifies each row. Two rules come built in: the value must be **unique**, and it can **never be NULL**. Every table gets exactly one primary key.

You've been making one since chapter 05 with the recipe line. This chapter explains what every word of it does, and when you'd write something different.

## Why does it matter?

Let's see what goes wrong without one. Work in `practice`:

```sql
CREATE TABLE guests (name text, table_number integer);
INSERT INTO guests VALUES ('Sam', 4), ('Sam', 4), ('Priya', 2);
```

Two guests called Sam, both at table 4. Now one of them moves to table 7:

```sql
UPDATE guests SET table_number = 7 WHERE name = 'Sam';
```

```
UPDATE 2
```

Both Sams moved. There is **no way** to say "this Sam, not that one". They're identical in every column. You can't update one, you can't delete one, and no other table can point at one. The row has no identity.

A primary key fixes this once and for all: every row gets a value that belongs to it alone.

```sql
DROP TABLE guests;
```

## Real-world example

Two people called Sita Sharma live in the same town. The government doesn't tell them apart by name. It gives each a **citizenship number**. That number:

- is different for every person (unique),
- everyone has one (not null),
- never changes, even if she changes her name (stable),
- is what every other office uses to refer to her (other tables point at it).

That's a primary key. A library barcode does the same for two copies of the same book.

## How it works

### The recipe, word by word

```sql
id integer PRIMARY KEY GENERATED ALWAYS AS IDENTITY
```

| Part | Meaning |
|---|---|
| `id` | The column's name. Just a convention; you could call it anything. |
| `integer` | Whole numbers. |
| `PRIMARY KEY` | This column identifies rows. Implies `UNIQUE` and `NOT NULL`, and creates an index (chapter 31) so lookups by id are fast. |
| `GENERATED ALWAYS AS IDENTITY` | PostgreSQL keeps a counter and fills in the next number on every insert. `ALWAYS` means you're not allowed to supply your own. |

That counter is called a **sequence**. It's a tiny object that lives next to the table and remembers "the next number is 10". You saw it in `\d books` as `generated always as identity`.

### Natural keys and surrogate keys

There are two ways to pick a primary key:

- A **natural key** is a real-world identifier that already exists: an email address, an ISBN, a citizenship number, a country code.
- A **surrogate key** is a made-up number with no meaning outside the database: `id`.

Natural keys sound appealing. Why invent a number when a book already has an ISBN? Here's why:

| Problem with natural keys | Example |
|---|---|
| They change | People change their email. Then every table pointing at the old one breaks. |
| They're sometimes missing | Old books have no ISBN. *Beowulf* has no author. |
| They repeat in surprising ways | The same book gets a new ISBN for each edition. Two products can share a barcode across countries. |
| They're long and easy to mistype | `978-0-547-92822-7` vs `7` |

A surrogate `id` has none of these problems: always present, never changes, short.

**The advice this course follows:** give nearly every table a surrogate `id`, and put `UNIQUE NOT NULL` on the natural candidates (like `email`) so they're still protected. You get identity *and* the real-world rule.

The exception: tiny reference tables where the natural key really is stable and universal, like a `countries` table keyed by its two-letter code. You'll try that in the exercises.

### `ALWAYS` vs `BY DEFAULT`

```sql
id integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
```

`BY DEFAULT` means "fill it in for me *unless* I give a value". It's useful once: when you're importing old data that already has ids. Otherwise it's a trap:

```sql
CREATE TABLE tickets (
  id integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
  subject text NOT NULL
);
INSERT INTO tickets (id, subject) VALUES (1, 'Printer broken');   -- you chose 1
INSERT INTO tickets (subject) VALUES ('Login not working');        -- counter gives... 1
```

```
ERROR:  duplicate key value violates unique constraint "tickets_pkey"
DETAIL:  Key (id)=(1) already exists.
```

The counter didn't know you'd used 1. After an import, you have to tell it where to continue:

```sql
ALTER TABLE tickets ALTER COLUMN id RESTART WITH 100;
```

Stick with `ALWAYS` unless you're importing. It can't get out of step, because it never lets you choose.

### `serial`: the old way

You'll see this in tutorials, older code, and Stack Overflow answers:

```sql
id serial PRIMARY KEY
```

`serial` does the same job as `GENERATED BY DEFAULT AS IDENTITY`, in an older style with a few quirks around permissions and copying tables. Read it as "auto-numbered id". In your own code, write the `IDENTITY` form. It's the standard, and it's what PostgreSQL recommends.

### Gaps are normal

Ids will have gaps. A failed insert uses a number. A rolled-back transaction uses a number. Deleting a row leaves a hole. Your table might have ids 1, 2, 5, 6, 9.

**This is fine.** An id is a name, not a position. Don't try to "fix" gaps, don't reuse a deleted id, and don't assume the biggest id equals the number of rows. If you need row numbers for display, chapter 28 has a proper tool for that.

### `integer` or `bigint`?

`integer` runs out at about 2.1 billion. For a table of books, customers, or products, you'll never get there. For a table that logs every click, message, or sensor reading on a busy system, you might. Changing the type later is possible but slow on a huge table, so many teams write `bigint` for every id from day one:

```sql
id bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY
```

Either is fine for this course. Just know why you'd see both.

### Composite primary keys

Sometimes no single column identifies a row, but a **combination** does. A student can take many courses and a course has many students, but each (student, course) pair happens once:

```sql
CREATE TABLE enrollments (
  student_id integer NOT NULL,
  course_id integer NOT NULL,
  PRIMARY KEY (student_id, course_id)
);
```

The primary key goes at the end, listing both columns. Now the same student can't enroll in the same course twice, but can enroll in many courses. This is the main tool of [chapter 17](../17-many-to-many-relationships/notes.md).

### UUIDs: another kind of surrogate key

Instead of counting 1, 2, 3, some systems use a **UUID**: a random 128-bit value that looks like `a3f1c2d4-8e5b-4c7a-9f2e-1b3d5a7c9e0f`.

```sql
id uuid PRIMARY KEY DEFAULT gen_random_uuid()
```

Why? Two reasons. Ids can be generated anywhere (a phone app that's offline, two databases that later merge) without clashing. And they can't be guessed: with numbered ids, `/orders/1043` invites someone to try `/orders/1044`.

The cost: they're long, they don't sort by creation order, and they're horrible to type in psql. For this course, and for most apps, numbered ids are the right call.

### Using the key

Everything you learned in chapter 10 leans on the primary key:

```sql
UPDATE books SET year = 1938 WHERE id = 1;
DELETE FROM books WHERE id = 7;
```

`WHERE id = ...` can never match the wrong row, because no two rows share an id. That's why careful people prefer it.

## Common mistakes

**1. A table with no primary key**

The two Sams. Every table gets one, even tiny ones, even "temporary" ones.

**2. Using something that can change**

Email, username, phone number. The day it changes, everything pointing at it breaks. Surrogate `id`, plus `UNIQUE` on the natural column.

**3. Treating ids as row numbers**

"Show the 5th customer" is `ORDER BY ... LIMIT 1 OFFSET 4`, not `WHERE id = 5`. Ids have gaps.

**4. Supplying ids by hand**

With `ALWAYS`, PostgreSQL refuses, which is the point. With `BY DEFAULT`, it lets you, and the counter gets out of step. Let the database count.

**5. A primary key on `name`**

Names repeat, change, and have spelling variations. Never.

**6. Two "primary keys"**

A table has exactly one. If two columns each need to be unique, one is the `PRIMARY KEY` and the other gets `UNIQUE`.

## Quick recap

- A primary key identifies each row: **unique**, **never NULL**, one per table.
- `id integer PRIMARY KEY GENERATED ALWAYS AS IDENTITY` is a **surrogate key**: PostgreSQL counts for you, and you can't override it.
- Prefer surrogate ids over natural keys (email, ISBN), and protect natural candidates with `UNIQUE NOT NULL` instead.
- Gaps in ids are normal. Never reuse or "fix" them.
- `serial` is the old spelling. `BY DEFAULT` is for imports only. `bigint` for tables that might get enormous. `uuid` when ids are made in many places.
- A **composite** primary key, `PRIMARY KEY (a, b)`, identifies rows by a pair. Chapter 17 uses it heavily.
