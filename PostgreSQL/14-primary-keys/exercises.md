## Exercise 1 (Easy): The two Sams

1. Recreate the `guests` table from the notes, **without** a primary key. Insert the two Sams and Priya.
2. Try to delete **only one** Sam. Write a comment explaining why you can't.
3. Drop the table and recreate it with the `id` recipe. Insert the same three guests.
4. Now delete one Sam, by id. Confirm the other is still there.

## Exercise 2 (Easy): Natural or surrogate?

For each table, say whether you'd use a natural key or a surrogate `id`, and which column(s) you'd protect with `UNIQUE`:

1. `customers` (name, email, phone)
2. `countries` (two-letter code, name)
3. `books` (title, isbn, author)
4. `cars` (license plate, make, model, owner)
5. `employees` (name, badge number, national id number)
6. `currencies` (three-letter code like NPR, USD; name)

Write one sentence of reasoning for each.

<details>
<summary>Hint</summary>

Ask: can this value change? Can it be missing? Is it short and stable enough that you'd be happy typing it in a `WHERE` a hundred times? Country and currency codes usually pass; almost everything else doesn't.

</details>

## Exercise 3 (Medium): A natural key that works

Create a `countries` table with a **natural** primary key: `code text PRIMARY KEY`, plus `name text NOT NULL UNIQUE`. Add a `CHECK` so the code is always exactly 2 characters.

1. Insert Nepal (`NP`), India (`IN`), and the United States (`US`).
2. Try to insert `'NPL'`. Try to insert `'NP'` again. Try to insert a country with no code.
3. Run `\d countries`. What's the primary key's index called?

Then a thought experiment, as a comment: suppose 40 other tables refer to countries by this code, and one day a country changes its code. What has to happen? (Chapter 16 will show a tool that helps, but the pain is the point.)

## Exercise 4 (Medium): The import trap

1. Create a `tickets` table with `GENERATED BY DEFAULT AS IDENTITY` and a `subject text NOT NULL`.
2. "Import" three old tickets with ids 1, 2, 3 by supplying the ids yourself.
3. Insert a new ticket **without** an id. Read the error.
4. Fix the counter with `ALTER TABLE ... RESTART WITH ...`, so the next automatic id is 4. Insert the new ticket again and check its id.
5. Drop the table and recreate it with `GENERATED ALWAYS`. Try step 2 again. What happens, and why is that better most of the time?

<details>
<summary>Hint</summary>

`ALTER TABLE tickets ALTER COLUMN id RESTART WITH 4;`

</details>

## Exercise 5 (Challenge): Composite keys at the cinema

A cinema sells seats for screenings. Create `seat_reservations` with `screening_id integer NOT NULL`, `seat_number text NOT NULL`, `customer_name text NOT NULL`, `reserved_at timestamptz NOT NULL DEFAULT now()`, and a **composite** primary key on the screening and the seat.

1. Reserve seat `'A1'` and `'A2'` for screening 1, and `'A1'` for screening 2. All should work.
2. Try to reserve `'A1'` for screening 1 again. It must fail. Copy the error's `DETAIL` line.
3. Answer in comments:
   - Why doesn't this table need an `id` column?
   - Someone suggests adding an `id` anyway "so it's like our other tables". If you did, what constraint would you **have** to keep, or the double-booking bug comes back?

<details>
<summary>Hint</summary>

If you add `id ... PRIMARY KEY`, the pair is no longer the primary key, so you'd need `UNIQUE (screening_id, seat_number)` to keep the rule. Either design is valid; the rule is what matters.

</details>
